The previous Core was replaced because it automatically treated XP as the entire relationship state and could create CASE 4 from 500 XP without an accepted dating request.

==================================================
RELATIONSHIP ID
==================================================

Function created/retained:

etherID(playerA, playerB)

UUIDs are compared and sorted so:
PLAYER A + PLAYER B
=
PLAYER B + PLAYER A

Relationship storage uses:
{etherlove.couple.%id%.*}

==================================================
CORE DATA
==================================================

Each relationship now initializes:

{etherlove.couple.%id%.created}
{etherlove.couple.%id%.points}
{etherlove.couple.%id%.stage}
{etherlove.couple.%id%.status}
{etherlove.couple.%id%.last-interaction}

Initial values:

points = 0
stage = 0
status = SOLTEIRO
created = now
last-interaction = now

==================================================
XP SYSTEM
==================================================

Normal XP is clamped to:
0 → 500

Functions:

getRelationshipPoints(p1, p2)
setRelationshipPoints(p1, p2, points)
addRelationshipPoints(p1, p2, amount)

Negative XP is clamped at 0.
XP above 500 is clamped at 500.

Every XP modification updates last-interaction and recalculates the relationship CASE.

==================================================
CASE SYSTEM
==================================================

XP-driven CASE thresholds:

CASE 0 = 0+ XP
CASE 1 = 100+ XP
CASE 2 = 200+ XP
CASE 3 = 300+ XP

400 XP is the minimum required to send /NAMORAR.

CASE 4 is NOT automatically generated by reaching 500 XP.
CASE 4 means NAMORANDO and requires an accepted dating request.

CASE 5 means NOIVO and requires the engagement transition.
CASE 6 means CASADO and requires the special marriage event.

==================================================
CASE UPDATE LOGIC
==================================================

updateRelationshipStage(p1, p2) now separates XP progression from relationship states.

CASE 0-3 are calculated automatically from XP.

CASE 4-6 are state/event driven.

CASE 4 can regress to CASE 3 if XP falls below 400.
When that regression occurs, status becomes SOLTEIRO.

CASE 5 and CASE 6 are currently preserved by the automatic XP stage updater; their later negative-XP/event behavior still requires a deliberate specification decision before implementation.

==================================================
STATUS SYSTEM
==================================================

Functions:

getRelationshipStatus(p1, p2)
setRelationshipStatus(p1, p2, status)

Official status values:

SOLTEIRO
NAMORANDO
NOIVO
CASADO

State transition functions created:

setDatingRelationship(p1, p2)
setEngagedRelationship(p1, p2)
setMarriedRelationship(p1, p2)

These functions change both CASE and STATUS.

==================================================
RESET / DIVORCE FOUNDATION
==================================================

Function created:

resetRelationship(p1, p2)

Reset result:

XP = 0
CASE = 0
STATUS = SOLTEIRO

RelationshipID is preserved.

The function is the Core foundation for the future /DIVORCIO implementation.

==================================================
HELPERS
==================================================

Existing/updated helpers:

getStageName(stage)
hasStage(p1, p2, minimum)
canStartDatingRequest(p1, p2)

canStartDatingRequest currently checks:

- XP >= 400
- CASE = 3
- relationship STATUS = SOLTEIRO

Global exclusivity checks against other relationships are NOT yet implemented in this function and remain part of the future relationship-state/request system.

==================================================
AUDIT FINDINGS FROM REMAINING FILES
==================================================

01-etherlove-utils.sk:

Current request system is incomplete.
Requests currently store type but do not yet contain all required request metadata/expiration rules.
Cooldowns are currently player-based for /RP and /AB and pair-based for /BJ.
These rules must be reconciled with the final specification before implementation.

02-etherlove-interactions.sk:

Current /RP loops through every other player and increases all existing relationships.
This is incompatible with pair-specific progression and must be redesigned.
Current /AB and /BJ values/rules also do not match the final specification.

03-etherlove-progression.sk:

Current /namorar only checks CASE and does not yet enforce the final 400 XP requirement, dating exclusivity, target availability, or full acceptance behavior.
Current marriage logic is too simplified.
A ceremonialist permission already exists, but the actual event system still needs to be rebuilt.

04-etherlove-interface.sk:

A prototype /el relationship menu already exists.
It currently displays existing relationships, CASE and points, but it must be redesigned around the final relationship/status model.

==================================================
IMPORTANT ARCHITECTURAL RULE
==================================================

XP != CASE != STATUS

XP represents relationship progression/quality.
CASE represents the relationship stage/state.
STATUS represents the affective relationship state.

They must not be collapsed into one variable.
